# Hatchet Hermes Bridge

This is the local-only bridge and execution ledger for Hatchet-to-Hermes
experiments. It is intentionally narrow: Hatchet workers submit bounded jobs,
the bridge records an idempotency key before any external effect, and Hermes
execution runs behind allowlisted actions.

The bridge is not a generic command runner and must not receive Hermes
credentials, provider keys, browser credentials, GitHub tokens, Linear tokens,
or session state from Hatchet workers.

## Purpose

The bridge is the factory's local ledger and safety boundary between Hatchet
workflow events and Hermes/provider side effects. It solves four problems:

- It records every requested factory effect behind a stable idempotency key
  before any external action can run, so retries and duplicate events converge
  on the same job instead of creating duplicate PRs or comments.
- It owns the factory attempt lineage for real and dry-run execution, including
  generation, branch, prior-attempt, and retry context used to decide whether an
  effect is allowed.
- It uses durable outboxes to hand committed work back into Hatchet and
  inspection/recovery flows without losing messages across process crashes or
  service restarts.
- It keeps Hatchet workers narrow: workers can submit, observe, and transition
  bounded bridge jobs, while credentials and provider-specific side effects stay
  behind scoped services such as Hermes and the lifecycle writer.

This is separate from the factory lifecycle writer outbox, which is only for
Linear comments.

## Runtime publication and migration boundary

The checkout is development input, never runtime authority. Bridge services and
timers execute only from the root-owned immutable release selected by
`/docker/driftward/hatchet/releases/bridge/current`; that symlink is switched
atomically by `bridge/publish-release.sh`. Publication rejects dirty relevant
source and extracts a named Git commit with `git archive`; `MANIFEST.json` and
`RELEASE_METADATA.json` bind every deployed path/mode/digest to that commit and
tree. A pre-existing version directory is reused only after complete manifest
verification. A release contains bridge Python and the fixed dispatcher trigger
only—never env files, credentials, database state, or GitHub/Linear/Hermes
credentials. Roll back by atomically repointing `current` to a previous
verified release, then restarting only as an approved rollout step.

Release hygiene is checked twice: the committed production archive is scanned
before its deterministic worker build, and the final allowlisted runtime tree
is scanned again before its manifest is written; the installer also scans its
complete staged publication set before quiescing any writer. The scanner
uses a fixed schema of secret-bearing keys for the protected Hatchet env files;
URLs, ports, booleans, and other configuration values are not secret inputs.
It requires root-owned, single-link, regular `0600` files for
`hatchet.env`, `hatchet-bridge.env`, `hatchet-workers.env`,
`hatchet-worker-bridge-executor.env`, and `hatchet-verifier.env`; missing,
symlinked, hard-linked, wrong-owner, wrong-mode, or wrong-type files fail
before scanning. `hatchet-worker-reconciliation.env`,
`hatchet-event-ingress.env`, and `factory-operator.env` are the only named
optional files, because their scoped units use optional environment files or
may not yet be installed. The
production scanner accepts no env-file path override.
Every configured required secret must be at least 12 bytes with four distinct
byte values. Inspection/recovery capability keys may be absent or explicitly
empty until their scoped workers are installed; all other classified keys must
be nonempty. Raw secret bytes plus standard/URL-safe Base64 (padded and
unpadded), hexadecimal, and percent-encoded forms are rejected without
reporting their values. Direct quoted string concatenation is checked only in
generated/source JavaScript, TypeScript, Python, and JSON; arbitrary encrypted
or cryptographic transforms are intentionally outside this boundary.

The production release gate is self-contained and never consults `PATH` or
fetches a scanner. It also rejects high-confidence credential, private-key,
and literal Bearer/Basic authorization-header formats while permitting source
redaction expressions and explicit placeholders. Pinned Gitleaks in Hatchet
Quality scans committed content independently in CI. Bytecode, caches, VCS
data, env files, backups, sockets, databases, logs, and other runtime state are
denied. Scanner output names only a path and rule.

Schema work is explicit. `hatchet_hermes_bridge.cli init` is the sole
migration/backfill/import path. The installer performs read-only predeploy,
private staging, a verified SQLite online backup, and a disposable-copy
migration/predeploy gate before it runs the staged release's single SQLite
transaction against the live ledger. Only after that transaction succeeds may
it publish configuration, units, and the release symlink; its commit trap
restores prior config/unit/symlink state if daemon reload or restart fails.
`serve`, scheduled `reconcile`, the
operator, dispatcher, and all ordinary runtime connections require the current
schema version and fail with `bridge migration is required before runtime
access` rather than performing DDL or legacy import.

An approved live migration has a quiesced window. Before taking its backup the
installer requires Factory `dry-run` and zero active jobs, attempts, leases,
and outboxes; records direct writer and HTTP-client service states; stops them;
then proves the bridge DB has no holders and the API is unavailable. The same
quiesced backup supplies both disposable and live migration. A failed
post-migration publication restores the database with SQLite's backup API,
removes WAL/SHM after all writers stop, verifies integrity, restores every
snapshotted target (including previously absent/dangling symlinks), and starts
only the services that were previously active. The reconciler remains disabled
for the first post-incident rollout until a separately approved smoke test.
`hatchet_hermes_bridge.runtime` is the authoritative writer inventory: bridge,
reconciler, outbox dispatcher, and root-only operator are direct SQLite
writers; executor and reconciliation workers are paused HTTP mutation clients.
The installer runtime-masks that inventory, then holds an exclusive advisory
`flock` on the fixed root-owned
`/run/driftward-hatchet-bridge/maintenance.lock`. Every writable runtime
connection holds a shared flock for its whole SQLite connection lifetime, so a
new installer cannot proceed while a writer remains. Lock-file existence alone
is harmless. The migration process may use only inherited fixed descriptor 3;
it verifies the descriptor's device/inode and exclusive lock against that fixed
path. There is no environment or CLI bypass. Read-only predeploy remains
allowed. Backup database and checksum files are root-owned `0600`, fsynced,
integrity-checked, and named with the release commit before disposable or live
migration starts. While the installer holds that lock it writes root-owned
runtime drop-ins under `/run/systemd/system/<writer>.d/` with a negated
`ConditionPathExists` against its maintenance-active sentinel. Drop-ins are
additive even when the base unit lives in `/etc`; do not use runtime masks for
this barrier because `/etc` has higher unit-file precedence. The barrier covers
currently absent planned units too, then the installer reloads systemd, stops
only loaded units, and proves the condition/drop-in/inactive postconditions.

If an installer hard-blocks, do not remove `recovery-blocked`, runtime barrier
drop-ins, or stale runtime masks by hand. After a reviewed recovery release,
run `bash hatchet/bridge/recover-blocked.sh`. It requires a root-only captured
state/ledger record, proves the schema and immutable ledger are unchanged,
cleans only owned stale `/run` mask symlinks under the active condition barrier,
restores the captured old service state (except the incident-disabled
reconciler), and removes the marker only after old bridge health succeeds. It
never migrates or starts a new rollout; missing or mismatched evidence remains
blocked.

The one pre-capture incident has a distinct, one-way path: after the recovery
PR is merged, compute the marker and approved backup SHA-256 values without
printing either file, then run
`bash hatchet/bridge/recover-safe-down.sh --yes --backup /root/driftward-backups/hatchet/bridge-<timestamp>-before-<40-hex>.sqlite --checksum <64-hex> --marker-sha256 <64-hex> --marker-mtime <epoch-seconds>`.
It first acquires the fixed exclusive lock and condition barrier, then opens
the marker, backup and checksum with `O_NOFOLLOW`. The backup must be a direct
child of the protected backup directory with the exact name shape, root:root
`0600`, one link, a strict canonical-name-bound checksum sidecar whose filename
text is only the validated backup basename or its exact canonical absolute
path, SQLite integrity,
and a matching held descriptor. Proof covers the schema-0 immutable/effect
ledger and the single authoritative publication-target inventory: current and
failed release targets plus routing must be absent; every allowed pre-existing
config, env, policy, verifier, and unit target must be a root-owned regular
file whose mode, ctime, and mtime predate the marker. Any partial or unexpected
publication blocks recovery.

The checksum sidecar accepts exactly one `sha256sum` record for the already
canonical protected backup: its literal basename or its literal canonical
absolute pathname (with GNU's optional binary `*` marker). The sidecar field
is opaque text and is never resolved, normalized, or used to select a path;
raw CLI spellings, other directories, traversal, prefixes, and wildcards are
rejected.

The command writes an append-only root-only incident directory keyed by the
marker digest/inode identity, archives the marker, and creates a digest-bound
transition record with no-clobber files and directory fsyncs. It hands the
normal installer FD 3 (exclusive lock), FD 4 (archive-linked transition), and
held evidence FDs; installer adoption recomputes the proof while the barrier
remains active before it can stage a release. The original marker is only
removed after new-release health and a durable completion record. It never
starts the old mutable-checkout bridge; a proof mismatch or interruption
remains safe-down with the barrier and marker retained.

### Reviewed transition supersession

The original v1 transition is immutable and remains readable forever. Ordinary
v1 adoption still requires the exact `code_commit` recorded by v1; do not edit
or relabel it to make a later checkout adopt it.

The existing live v1 transition remains bound to
`aee9809d2a9b712572e13878d63f51854735c558`. When the final reviewed commit
from PR #149 is merged to `main`, it may become a v2 successor only through
the same reviewed-receipt path below: its GitHub merge commit is the successor
and its final PR head is separately bound as the approved review identity. The
hermetic v1→v2→v3 and SIGKILL replay matrices exercise that immutable-parent
successor contract; they never retag or relax v1.

After a successor recovery change has been merged, an operator may create a
new active successor without running an installer:

```bash
bash hatchet/bridge/recover-safe-down.sh --yes --supersede \
  --parent-transition-sha256 <exact-parent-sha256> \
  --parent-generation <exact-parent-generation> \
  --parent-code-commit <exact-parent-code-commit> \
  --backup /root/driftward-backups/hatchet/bridge-<timestamp>-before-<40-hex>.sqlite \
  --checksum <approved-backup-sha256> \
  --marker-sha256 <exact-marker-sha256> --marker-mtime <epoch-seconds> \
  --successor-commit <merged-main-commit> --successor-pr <merged-pr-number> \
  --approved-pr-head <exact-reviewed-pr-head-sha>
```

#### One-time descendant marker attestation

The pre-capture incident may contain a v1 archive that records the original
blocking marker while a failed rollback later rewrote that same inode to the
literal terminal reason `safe-down fresh-install-failed`. That write does not
make the new bytes v1 evidence. Do not edit v1, copy a marker over it, or use
the ordinary supersession command to paper over the mismatch.

Only the reviewed incident path may use the additional, explicit operator
attestation arguments below. Every value is measured immediately before the
command; arguments are identifiers and hashes only, never marker/backup
contents or credentials.

```bash
bash hatchet/bridge/recover-safe-down.sh --yes --supersede \
  --attest-descendant-marker \
  --parent-transition-sha256 <v1-sha256> --parent-generation 1 \
  --parent-code-commit <v1-code-commit> \
  --old-marker-sha256 <v1-marker-sha256> --old-marker-dev <dev> \
  --old-marker-ino <inode> --old-marker-mtime-ns <mtime-ns> \
  --marker-sha256 <current-terminal-marker-sha256> --marker-dev <dev> \
  --marker-ino <same-inode> --marker-mtime <epoch-seconds> \
  --marker-mtime-ns <mtime-ns> \
  --terminal-marker-reason 'safe-down fresh-install-failed' \
  --backup <approved-backup-path> --checksum <approved-backup-sha256> \
  --successor-commit <reviewed-merged-main-commit> \
  --successor-pr <merged-pr-number> --approved-pr-head <reviewed-pr-head>
```

Under the existing read-only lock/barrier descriptor proof, this mode proves
the immutable v1 archive/link and recorded old marker, then opens the current
marker with `O_NOFOLLOW`. It accepts only that literal terminal reason, the
exact supplied current SHA-256/device/inode/nanosecond mtime, and the old
inode as an additional incident constraint. It independently reproves the
protected backup and sidecar, schema-zero/zero-work ledger, and absent
publication targets. Ambiguous publication/supersession journals, a reused or
tampered attestation, any other terminal text, stale identity, altered DB,
backup, target, or reviewed provenance fail closed.

Before v2 is written it creates one root-only `O_EXCL` descendant-attestation
object in the immutable incident directory and fsyncs it. The v2 record binds
the attestation hash and proof digest plus both marker identities. Thus v2
adoption validates the current marker against the descendant object and the
complete parent chain; it never claims that current bytes still match v1.
SIGKILL/replay at the attestation write/fsync and every ordinary successor
boundary converges to the identical archive/link/journal state without
changing the marker, ledger, services, or publication targets.

#### Future rollback marker lineage

`install.sh` never redirects into `recovery-blocked`. The marker writer is
internal-only: it runs through the already-held maintenance lock plus the same
inherited sentinel/drop-in descriptor and no-holder proof used by standalone
supersession. A direct lock-only `safe_down_recovery.py update-marker-lineage`
invocation fails closed.

Each active transition owns an immutable incident-scoped sequence of
`marker-lineage-…-gN.journal` events and matching immutable records. A new
transition, completion, or later failure therefore cannot collide with or be
poisoned by an old attempt's journals; old incident evidence is retained
forever. If there is no active transition, each update creates its own
deterministic immutable unbound incident from the exact current marker
descriptor/hash plus requested reason. Its input must be either the canonical
initial safe-down marker or the exact committed output of one fully validated
prior unbound incident. The prior journal is provenance only: it is never
reused as the new event or allowed to block a completed successor. Prepared,
tampered, extra, stale, or untracked evidence fails closed.

Before appending `prepared`, the state machine creates a deterministic
root-only `O_EXCL|O_NOFOLLOW` temporary marker, writes and fsyncs it, then
records its exact path, SHA-256, device, inode, mode, link count, and
nanosecond mtime in `prepared`. Replay before rename requires that exact temp
descriptor; replay after rename requires that the live marker is the exact
same descriptor, not merely identical text. Symlinks, links, replacement
inodes, and same-content substitutions fail closed. A crash before `prepared`
leaves an unauthorised orphan temp and also fails closed for investigation.

Each committed event writes an immutable lineage object bound to its transition
or unbound incident, old/new marker identities, and reason. A future successor
references the exact final transition lineage hash; v2+ descendants again
remain strict. This state machine writes no DB row, starts no unit, changes no
publication target, enables Factory mode, or changes reconciler state.

This command requires an already-installed active maintenance barrier and an
existing exclusive maintenance lock. Its standalone branch only opens and
locks that existing capability, then opens the sentinel and every condition
drop-in with `O_NOFOLLOW`, retaining those descriptors and their
device/inode/content-digest proof through the shell-to-Python exec boundary.
An exact systemd `LoadState=not-found` planned unit still requires its expected
validated drop-in source file, but has no loaded-unit `DropInPaths` or active
state to prove; every other load-state result remains fail-closed.
It rechecks those descriptors, writer/reconciler states, and DB holder state
immediately before writing the successor to prove the host is already quiesced.
It never creates or removes a barrier, drop-in, runtime mask, or lock; it never
stops, starts, masks, unmasks, reloads, resets, enables, or disables a unit.
If the host is not already quiesced it fails closed. Ordinary safe-down
recovery retains its separate barrier-installation behavior. The exclusive
lock serializes cooperative mutators; this is not a claim to protect against a
malicious root process.

After this read-only barrier proof it reproves the active parent archive/link,
marker, approved backup and checksum, live schema-zero ledger, and every
publication target using no-follow descriptors. A publication journal never
shortcuts this supersession proof. It rejects dirty/untracked or non-current
source trees and uses root's read-only GitHub API access to prove that the
supplied PR is merged to `main` at the exact successor commit. Squash semantics
are explicit: the approved PR head is a separate supplied identity, while the
successor is the GitHub merge/current commit. The receipt requires both repos
to be this repository, the canonical PR URL, base `main`, and an exact
single-parent squash relation: GitHub/local base SHA is the sole parent of the
GitHub/local merge commit and both trees agree. The canonical sanitized receipt
binds all of those fields and its SHA-256 is persisted. No GitHub credential
reaches Hatchet.

Each v2+ transition copies the complete v1 proof and records its parent hash,
generation, code commit, immutable parent archive name, successor tree, and
reviewed-release receipt. The command writes the successor archive with
`O_EXCL`/`0600`, fsyncs it and its directories, appends a fsynced journal,
creates a temporary hard link, fsyncs, atomically renames that link over the
active transition, and fsyncs again. Replay at every boundary either converges
to that same successor or blocks; it never mutates/deletes a parent or the
marker. A v2 may be superseded by v3 in the same way. Adoption validates the
entire chain, reruns clean-checkout and untracked-file checks, and requires the
current HEAD, parent, and local tree to equal the final reviewed successor
merge commit/parent/tree. A v2+ adoption always strictly compares the live DB
and every publication target to the archived proof; no publication journal can
relax that equality.

Supersession is standalone: it does not install, migrate, touch the bridge DB,
start/restore services, publish targets, change Factory mode, or remove the
safe-down marker. It only advances the archived active-transition capability;
the later ordinary recovery invocation still performs adoption and health.

Publication is a separate crash-recoverable transaction. Before the first
target mutation, the installer records a root-only `0600` append-only journal
under the bridge state directory with the complete pre-snapshot, desired
release manifest, transition identity, and ordered operation records. It
fsyncs every journal record and parent directory. A later installer invocation
refuses normal staging while a journal is incomplete; the explicitly approved
safe-down wrapper recognizes only a journal bound to its archive-linked
transition, validates and rolls it back through the existing publication
transaction, restores the recorded snapshot, appends a durable `rolled_back`
safe-down v1 recovery record, and only then performs strict adoption proof
before a fresh install. No adoption path treats journal presence as proof.
This applies even after the publication `committed` record: publication alone
is not the recovery commit boundary, because health and marker removal have
not completed. Other journals remain blocked rather than being generalized
into a recovery interface.
The commit helper owns snapshot, publication, and rollback, including release
directories, symlinks, transient names, and newly-created directories.

Before and after migration the installer hashes canonical rows in immutable
job/attempt/event/effect-sensitive tables without logging their values. Any
unexpected mutation triggers rollback; only schema additions and deterministic
append-only conflict-resolution markers may change. The legacy bridge
reconciler timer stays disabled and both it and the static reconciler service
stay inactive after either success or rollback. The supported automatic
reconciliation path is now `driftward-hatchet-worker-reconciliation.service`;
running the bridge `reconcile` CLI without `--dry-run` is break-glass recovery,
not a scheduled runtime component. The installer never relies on runtime masks,
because they cannot override locally installed `/etc/systemd/system` unit
files.

Historical legacy receipt reconciliation is not fresh retry eligibility.
Already-imported rows prove their exact source-to-receipt lineage using only
path-scoped evidence: direct bridge `pr_url`, documented bridge event result
objects, and the exact inspection result/request schema. Arbitrary nested
`url` or `branch` metadata is ignored and therefore cannot satisfy a real
artifact requirement. A repository can now be disabled only for a fully
proved historical receipt; intake and operator retry routing still require an
enabled current route.

Hatchet owns orchestration. The bridge owns external-effect fencing. Driftward
Hermes owns execution authority and credentials.

## Data Model

The bridge stores both a materialized job row and append-only events:

```text
bridge_jobs
  idempotency_key unique
  state
  requested_action
  deterministic branch
  external refs such as commit_sha and pr_url

bridge_events
  append-only transition history
```

The job row is the fence used by retries. The event table is the audit trail.

`factory_attempts` is a separate generationed operator ledger. A fresh retry
is not an update of the old active idempotency key: generation 2 and later use
`hatchet:work-item:linear:ENG-X:create_draft_pr:<mode>:attempt:<generation>`
and therefore receive a new deterministic branch. `factory_attempt_events` is
append-only. A reservation atomically creates the attempt, bridge job, and
audit trail with immutable retry lineage. Legacy generation-one jobs remain
readable but a real imported legacy job cannot complete through the modern
verifier path.

Every reservation also writes one accepted-event outbox row in the same SQLite
transaction. The dispatcher leases, delivers, and acknowledges that immutable
row; a crash before acknowledgement replays the same event and never reserves
another job. Real jobs without a valid generationed `factory_attempt` lineage
fail before Hermes; supported legacy real jobs must be imported as generation
one by predeploy. The executor takes a separate execution lease, then records
an atomic single-use `effect_authorized` phase before Hermes. Before that phase
cancellation or expiry prevents authorization. Afterwards the authority is
irrevocably assigned to exactly that owner, epoch, and opaque fence token:
cancellation is reported as too-late/in-flight, expiry cannot transfer it, and
only that owner may settle or commit the eventual provider receipt. An observed
effect settlement preserves that authorization record rather than releasing it;
post-effect and verification states are permanently non-claimable.

`/docker/driftward/hatchet/releases/bridge/current`, not from the mutable

```text
GET  /health
GET  /jobs?limit=<1..250>
POST /jobs
GET  /jobs/<job_id_or_idempotency_key>
GET  /jobs/<job_id_or_idempotency_key>/events?limit=<1..250>
POST /jobs/<job_id_or_idempotency_key>/transitions
POST /jobs/<job_id_or_idempotency_key>/correlations
POST /jobs/<job_id_or_idempotency_key>/verification/lease
POST /jobs/<job_id_or_idempotency_key>/verification/lease/claim
POST /jobs/<job_id_or_idempotency_key>/verification/observation
POST /jobs/<job_id_or_idempotency_key>/verification/completion
POST /reconciliation/findings
```

Every bridge endpoint requires the local bearer token generated by
`bridge/install.sh`. The installer verifies authenticated `/health` before
workers are installed; unauthenticated loopback requests are rejected.

`POST /jobs` accepts:

```json
{
  "idempotency_key": "hatchet:workflow-run:create_pr:ENG-35",
  "requested_action": "create_draft_pr",
  "hatchet_workflow_run_id": "optional",
  "hatchet_step_run_id": "optional",
  "payload": {
    "repo": "Driftward-LLC/driftward-host",
    "linear_issue": "ENG-35"
  }
}
```

Submitting the same idempotency key with the same action and payload returns
the existing job. Submitting the same key with different intent returns a
conflict.

The retry operator intentionally has no TCP endpoint and no bridge/verifier
token. Its independent root-owned `0600` env file contains
`HATCHET_FACTORY_OPERATOR_TOKEN` plus Hatchet client connection settings; it
does not receive bridge, verifier, GitHub, Linear, Hermes, Docker, or browser
credentials. Its socket is `0600`. Its typed API accepts only
preview/reserve/list/show/cancel. It is not a command runner. The executor can
read a job's retry cancellation marker through the ordinary bridge API and stops
before a provider effect; cancellation after an effect is observational only and
never closes or deletes the PR.

Preview, list, and show open the bridge SQLite database with `mode=ro` and do
not migrate, backfill, enable WAL, or append events. A missing/unmigrated
database reports `bridge predeploy is required before read-only operator
access`. The installer/write service performs migration and legacy import.
Preview returns a trusted ingress snapshot digest. A write requires that digest
plus an explicit request ID, revalidates the ingress/routing/policy snapshot at
the reservation boundary, and rejects stale status/blocker/policy changes.

Prior PR inspection is an allowlisted `inspect_draft_pr_state` bridge action.
It accepts only the canonical enabled repository and an exact GitHub PR URL or
number, runs only through the bridge-executor outbox, and returns the bounded
sanitized shape `{repository,number,url,state,merged,draft,head_branch,head_sha,base_ref,reason}`.
The operator never runs Docker, Hermes, arbitrary commands, or prompts; while
inspection is pending/unavailable it blocks retry safely.

Inspection jobs are created only by the operator-owned attempt/artifact lineage;
the ordinary bridge `POST /jobs` endpoint rejects them. Their result and their
dedicated terminal `completed` transition are committed atomically, while
`completed` remains forbidden for real `create_draft_pr` jobs. The preview
snapshot includes the prior attempt, PR, inspection request, result digest,
observed time, state, merge/draft/head facts; reservation revalidates that
fence and rejects observations older than two minutes, a changed head SHA/base,
reopen, merge, unknown result, future timestamp, or a second concurrent intent.
The complete canonical fence is persisted in both the new attempt and immutable
bridge-job lineage and is re-observed before Hermes.

The ordinary bridge bearer cannot submit an inspection result or lease recovery.
The executor uses `HATCHET_HERMES_INSPECTION_TOKEN` only on the inspection
completion endpoint and includes the immutable inspection request key plus its
per-request capability. The
reconciler uses the separate `HATCHET_HERMES_RECOVERY_TOKEN` only on typed
recovery. Installers generate both in the protected bridge env and publish
each only to its scoped worker environment.

An authorized executor that disappears moves its attempt to
`effect_outcome_unknown`; it is never reclaimed automatically and blocks new
generations. The typed recovery path records durable, digest-checked inspection
evidence under an explicit recovery request key but never permits another
create authorization for that generation. Even trustworthy absence observation
is evidence for explicit human/new-generation action, not proof that the
authorized process did not call the provider. Unknown or conflicting evidence
remains operator-visible and blocks allocation.

A reviewed break-glass retry can supersede exactly one
`effect_outcome_unknown` attempt only through the root operator's
`force-absence` path. The host CLI derives the canonical repository and prior
head branch from trusted Factory state, collects a fresh GitHub branch/PR
absence proof, and sends that fixed evidence to the operator. Reservation then
revalidates the Linear snapshot, route, policy, prior attempt, expired
authorized lease, missing prior PR, and absence evidence before recording
`absence_superseded_unknown_attempt` and accepting the next generation in one
transaction. The old lease is preserved as audit evidence, and a superseded
attempt cannot later commit through the fenced execution endpoint.

The ordinary transition endpoint cannot terminalize a real factory job after
its durable attempt reaches `effect_authorized`, `effect_committed`, or a
verification/post-effect phase, regardless of whether its lease has since been
released. Failures before claim use the pre-effect worker path; effect commit,
cancellation, and verification use their dedicated typed endpoints. This
prevents a generic terminal write from racing a later authorization or
contradicting an already committed artifact.

The Unix socket records Linux `SO_PEERCRED` uid, pid, and best-effort passwd
account in the immutable attempt actor. This authenticates the local peer, not
an end-user session or TTY; caller-supplied actor fields are not accepted.

## State Flow

```text
accepted -> running -> effect_committed -> verification_pending -> ready_for_human_review
accepted -> failed
running -> failed
effect_committed -> failed
verification_pending -> failed
```

`effect_committed` truthfully means an external artifact exists. It is not an
implementation-success state. The bounded Hermes-side verifier must collect
the draft PR's repository, base, deterministic branch, draft status, Factory
App author, exact `Refs Linear ENG-X` line, changed-file scope, aggregate
GitHub check status, and reported local validation/secret-check evidence before
it can transition to `ready_for_human_review`. Each real payload carries an
immutable copy of a checked-in repository verifier policy: allowed and forbidden
paths, exact local commands, and one exact secret-check command.
Missing or unavailable evidence fails closed. A stale reconciler may recover
an artifact into `verification_pending` and re-deliver the original job for
bounded verification, but it must never infer verified readiness merely
because a draft PR exists.

Terminal jobs cannot be transitioned again. Retries read the existing job and
return its current state/result rather than starting a new external effect.
`effect_committed` and `verification_pending` retries resume verification for
the original deterministic branch and PR. The ledger persists the bounded
Hermes validation context plus a canonical, hashed verification receipt
(commit, aggregate GitHub check status, PR identity, file, local, and secret policy results)
before `ready_for_human_review` is allowed. `completed` is reserved for a
dry-run job; real jobs cannot enter that legacy terminal state.

The reconciliation worker sends stable finding keys to the bridge. The bridge
accepts only a strict finding schema, constructs the stored sanitized record,
and rejects unknown fields, arbitrary severities, raw payload/body fields, and
unknown kinds before it opens a write transaction. It deduplicates identical
retries and returns only newly recorded keys for Hatchet event emission; this
local ledger never mutates provider state.

Intake payloads preserve `source_event_key` and `source_delivery_id`; repeated
active-work submissions merge bounded correlation lists without changing the
effect idempotency hash. Reconciliation can therefore distinguish a consumed
delivery from an earlier unconsumed attempt. Legacy rows without this metadata
retain issue-level consumption fallback until they are naturally replaced.

Event emission is best-effort observability. A transient Hatchet event push
cannot undo or strand a durable bridge transition; stale real verification
states are re-delivered by reconciliation using the original job key.

Verification recovery uses one durable SQLite lease per original bridge job,
deterministic branch, PR, and `verify_draft_pr` action. Reconciliation acquires
the bounded lease before it emits a recovery event; the executor must claim the
same attempt before verification. Active or duplicate redelivery therefore
does not emit another pending or ready lifecycle marker. An expired unclaimed
or crashed attempt can be reacquired, while verified and failed terminal
transitions close the lease in the same database transaction. Operators can
inspect the sanitized lease event history through the job events endpoint.

The original `verification_context` (reported local and secret command results
at artifact creation) is immutable and stored separately from the later
receipt. A real verification completion supplies its claimed
`verification_attempt_id`; the bridge checks the live lease owner, expiry,
work-item, branch, and PR before accepting either verified-ready or a
verification failure. The receipt must exactly match that original command
context, immutable effect references, and the canonical policy. Older receipt
rows remain readable after migration, but cannot use the new completion path.
Before rollout, `bridge/predeploy-check.py --db <bridge.db>
--require-zero-legacy-ready` reports only the count of legacy ready rows and
blocks an unattended upgrade when an operator must inspect them.

### Historical Receipt Reconciliation

Predeploy and the write-time legacy importer share one pure compatibility
decision for old active-key rows. A row that already has one coherent
generation-one `legacy-import` receipt is reconciled as a no-op: its immutable
work item, mode, job, active-key lineage, deterministic branch, optional PR,
terminal legacy status, conflict state, and execution-lease state must still
agree. A duplicate receipt, conflict, active/pending effect, or any linkage
mismatch fails closed.

This historical reconciliation is deliberately separate from fresh retry
eligibility. It does not reapply a newer route policy to a durable receipt and
does not make a disabled route retryable; the root-only operator always reads
the current enabled routing and trusted ingress snapshot. For *unimported*
dry-run rows only, the exact historical
`dry-run://github/pr/<v4-uuid>` sentinel is ignored as non-artifact metadata.
All other dry-run URLs fail, and every unimported real row still requires an
enabled canonical route, one same-repository GitHub PR URL, and its exact
deterministic branch.

`factory_import_conflicts` and the v3
`factory_import_conflict_resolutions` rows are append-only historical evidence.
Schema v4 adds `factory_import_conflict_attestations`: an attestation is unique
by conflict key, resolver semantic version and contract digest, and normalized
routing-policy digest. Its immutable evidence digest, job, reason, decision,
operator, timestamp, and producing release SHA are auditable. The resolver
contract digest is fail-closed and derived from canonicalized ASTs for the
transitive resolver closure in `legacy_artifacts.py` (reconciliation and
artifact parsing) and `store.py` (artifact collection and evidence
construction), plus the enforced attestation contract values. Source positions,
comments, docstrings, formatting, and unreachable helpers are excluded; a
selected function, referenced local helper/constant/class, or contract change
changes the digest. The producing SHA is deliberately *not* part of the
identity: a commit-only equivalent release reuses the previous attestation
without row growth, while a reviewed resolver-contract or routing-policy
semantic change requires a fresh one.

The routing digest includes only registry version plus sorted `project_id`,
`repo`, and `execution_enabled` route values. Whitespace, JSON field order,
route order, and unrelated display fields do not change it. The installer
supplies the exact staged registry and release SHA to disposable and live
migrations. Read-only predeploy explicitly reports derivable v3 evidence and
attestations required; it may pass before migration. Both post-migration gates
also use `--require-current-attestations`, so no publication can proceed until
every currently selected semantic identity is attested. A changed source,
tampered v3 marker or attestation, unsupported reason, duplicate lineage, or
pending effect remains unresolved and blocks safely.

## Verifier Policy And Authority

All production processes use the explicit non-secret
`HATCHET_VERIFIER_POLICY_PATH`, normally
`/etc/driftward/hatchet-verifier-policy.json`. The bridge and worker installers
atomically publish the same root-owned catalog and compare its SHA-256 before
and after rename. A missing or unreadable path fails real verification closed;
checkout-relative paths are test-only.

`ready_for_human_review` additionally requires
`HATCHET_HERMES_VERIFIER_TOKEN` through `/etc/driftward/hatchet-verifier.env`.
This protected file is created empty by installers: an operator provisions the
secret separately. The ordinary bridge token cannot manufacture verified-ready
state. Roll back a policy publication by atomically restoring the prior catalog
at that path, then restart services only after the file digest is verified.

The normal transitions endpoint never accepts verification-terminal work. The
executor uses the verifier-authenticated completion endpoint for both verified
ready and verification failure, always with its claimed attempt ID. Ordinary
pre-effect and execution failures remain general bridge-token transitions.
`verification_context` is write-once and can be established only while moving
from `effect_committed` to `verification_pending`; recovery reads that stored
context and cannot rewrite it.

Recovery reserves and claims the verifier attempt before it reads or parses the
stored context. Once claimed, a missing or malformed context, red CI, timeout,
or other verification error completes through the verifier-authenticated
failure endpoint and closes that lease transactionally. If immutable PR/branch
references prevent a claim, the bridge leaves the job recoverable, records the
sanitized `verification_recovery_lease_unavailable` marker, and defers another
attempt instead of issuing an unauthorized terminal transition.

`bridge/verifier-env.sh provision` is the root-only, idempotent token
provisioning helper. It creates a 256-bit token in
`/etc/driftward/hatchet-verifier.env` with mode `0600` using atomic rename and
never prints it. `bridge/verifier-env.sh status` checks token presence and the
policy path/digest without disclosure. Both installers run those checks before
they enable or restart services.

Post-merge rollout: set Factory to dry-run, confirm no active real bridge jobs,
run the bridge installer and worker installer, run the preflight/status command
and `driftward-hatchet-smoke`, then restore real mode only after health and
queue gates pass. Rollback: return to dry-run, restore the prior policy/source,
rerun the installers, verify the same gates and smoke, and investigate any
legacy-ready count before restoring real mode.
